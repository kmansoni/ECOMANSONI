# Лучшие практики написания безошибочного кода
## Извлечено из анализа ECOMANSSI и open-source проектов

### 🔑 Основные принципы

1. **Типизация как первая линия защиты**
   - Использовать строгий TypeScript с `"strict": true` в tsconfig.json
   - Определять интерфейсы для всего состояния и API ответов
   - Избегать `any` типа везде где возможно
   - Пример: `interface NavigatorSettingsState` с 35+ строго типизированными свойствами

2. **Оборонное программирование**
   - Всегда проверять входные данные (null, undefined, диапазоны)
   - Валидировать данные на границах системы (API, пользовательский ввод)
   - Использовать clamping для числовых значений: 
     ```typescript
     setVolume: (v) => set({ volume: Math.max(0, Math.min(100, v)) })
     setLabelSizeMultiplier: (v) => set({ labelSizeMultiplier: Math.max(0.7, Math.min(1.5, v)) })
     ```

3. **Состояние по умолчанию**
   - Инициализировать ВСЕ свойства состояния дефолтными значениями
   - Никогда не оставлять свойства неинициализированными (предотвращает undefined)
   - Пример: все свойства в `useNavigatorSettings` имеют значения по умолчанию (линии 232-258)

4. **Безопасная работа с асинхронностью**
   - ВСЕГДА оборачивать async операции в try/catch
   - Предоставлять состояния загрузки для UX feedback
   - Предотвращать дублирующие запросы через флаги `isFetching`
   - Очищать таймеры и подписки при размонтировании компонентов

5. **Подписки и side effects**
   - Всегда очищать подписки (unsubscribe, removeChannel)
   - Использовать useEffect с правильным массивом зависимостей
   - Implement exponential backoff для повторных попыток соединения
   - Обрабатывать все состояния соединения: connecting, connected, error, disconnected

6. **Безопасность данных**
   - ВСЕГДА включать RLS для таблиц с пользовательскими данными
   - Проверять права на уровне БД (`auth.uid() = user_id`)
   - Использовать параметризованные запросы, избегать SQL инъекций
   - Очищать криптографические ключи в finally блоках:
     ```typescript
     destroy(): void {
       try {
         // ... cleanup
       } finally {
         this._rawBytes.fill(0); // Guaranteed cleanup
       }
     }
     ```

7. **Криптографическая безопасность**
   - Всегда выносить тяжёлые криптооперации в веб-воркеры или изоляты (не блокировать UI поток)
   - Использовать проверенные библиотеки (libsodium, oxidec, openmls-wasm) вместо самописной криптографии
   - Нулевать память после использования криптоопераций (использовать zeroize библиотеки или overwrite ArrayBuffer)
   - Валидировать длины ключей и данных перед обработкой (например, Curve25519 ключ = 32 байта)
   - Всегда использовать HKDF или аналогичные KDF для производства ключей из shared secrets
   - Включать forward secrecy и post-compromise security ( healing ) в протокол
   - Использовать аутентифицированное шифрование (AEAD) как AES-256-GCM или ChaCha20-Poly1305
   - Добавлять replay protection через счётчики и временные метки
   - Периодически выполнять полный рукообмен (X3DH/PQXDH) для восстановления после компрометации

8. **Архитектурные принципы**
   - Разделение ответственности: хранилище ≠ UI ≠ API слой
   - Единый источник истины для констант и конфигурации
   - Модульная организация (отдельные сторы для разных доменов)
   - Централизованная обработка ошибок с пользовательским feedback (toast notifications)

9. **Наблюдаемость**
   - Комплексное логирование для отладки
   - Пользовательский feedback через уведомления
   - Метрики производительности где критично
   - Health checks для внешних зависимостей

### 📋 Чек-лист для написания безошибочного кода

Перед каждым коммитом проверять:
- [ ] Все свойства состояния инициализированы дефолтными значениями
- [ ] Входные данные валидированы и sanitized
- [ ] Все async операции обёрнуты в try/catch
- [ ] Подписки и event listeners имеют соответствующую очистку
- [ ] RLS политики включены для всех таблиц с пользовательскими данными
- [ ] TypeScript строгий режим включен и нет ошибок типизации
- [ ] Нет консольных ошибок или предупреждений в dev режиме
- [ ] Пользователь получает feedback при ошибках и успехах операций
- [ ] Edge cases обрабатываются (пустые массивы, null значения, крайние диапазоны)
- [ ] Криптооперации вынесены в веб-воркеры или изоляты
- [ ] Криптографические ключи нулеваются после использования
- [ ] Длины ключей валидированы перед обработкой
- [ ] Используются аутентифицированные режимы шифрования (AEAD)
- [ ] Реализованы replay protection через счётчики

### 💡 Как применять эти знания

1. При начале новой функции/компонента:
   - Сначала определить типы интерфейсов
   - Добавить значения по умолчанию для всех свойств состояния
   - Реализовать валидацию входных данных
   - Добавить логирование ключевых операций
   - Обеспечить очистку ресурсов в finally блоках/useEffect возврате
   - Для криптоопераций: планировать вынос в веб-воркер, использовать zeroization

2. При ревью кода:
   - Проверять наличие типизации для всех параметров и возвращаемых значений
   - Искать места без валидации входных данных
   - Убедиться в наличии try/catch вокруг async операций
   - Проверить, что все подписки имеют соответствующую очистку
   - Верифицировать включение RLS для таблиц с пользовательскими данными
   - Для криптокода: проверять вынос в воркер, нулевание ключей, валидацию длин, использование AEAD

3. При отладке проблем:
   - Сначала проверять обработку edge cases (null, undefined, пустые значения)
   - Анализировать логи для последовательности операций
   - Проверять состояния загрузки и ошибок в UI
   - Верифицировать, что все изменения состояния проходят через валидированные setter
   - Для криптографии: проверять утечки ключей в памяти, правильность счётчиков, обработку реплея

Эти практики, примененные последовательно, позволяют уменьшить количество багов на порядок и сделать код более предсказуемым и поддерживаемым. Ключевое - не полагаться на удачу, а строить системы, которые предотвращают ошибки еще на этапе написания кода.
